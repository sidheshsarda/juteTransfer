# Final-Step Challan Inheritance — Design

**Date:** 2026-04-08
**Scope:** Bug fix in `src/jutetransfer/transfer.py`

## Problem

When a transfer chain returns to its source company (the "final step"),
the original MR is updated in place by `_update_original_mr()`. Currently
this function does not touch `challan_no` or `challan_date`, so the
finalized source MR retains the gate-entry challan info — not the
receiving challan info from the previous company in the chain.

For all *intermediate* steps the receiving MR already inherits the
previous step's invoice challan via `_create_mr(challan_no=..., challan_date=...)`
at `transfer.py:1318-1323`. The final step is the only one out of step
with this pattern.

## Requirements

1. After finalization, the source MR's `challan_no` must equal the
   `challan_no` of the sales invoice generated by the previous (selling)
   company on the final hop. (Same rule as intermediate steps: the
   invoice challan_no always wins.)

2. After finalization, the source MR's `challan_date` must follow the
   same `step.challan_date or invoice_challan_date` rule used by
   intermediate steps (user override wins, otherwise inherit from the
   invoice).

3. `mukam_id` on the source MR MUST remain untouched. (Current SQL
   already does not touch it — this requirement is a "do not regress"
   guarantee, not a new behavior.)

## Design

### Change 1 — `_update_original_mr()` signature & SQL

Add two optional parameters:

- `challan_no: Optional[str] = None`
- `challan_date: Optional[date] = None`

Add `challan_no = :challan_no` and `challan_date = :challan_date` to the
existing `UPDATE jute_mr SET ...` statement. When the caller passes
`None`, the column is left at its current value (use `COALESCE` or only
update when not None — see "Open detail" below).

`mukam_id` is intentionally NOT in the UPDATE — preserved as today.

### Change 2 — `save_transfer_step()` final-step branch

The final-step branch (`transfer.py:1282-1308`) already calls
`_create_sales_invoice()` and receives `(invoice_id, challan_date, challan_no)`
back. Today those return values are unused for the final step. Wire them
through to `_update_original_mr()`:

```python
invoice_id, inv_challan_date, inv_challan_no = _create_sales_invoice(...)
...
_update_original_mr(
    ...,
    challan_no=inv_challan_no,
    challan_date=step.challan_date or inv_challan_date,
)
```

This mirrors the intermediate-step call at line 1321 exactly.

### Open detail — how to express "leave column alone if None"

Two reasonable options:

- **A.** Always include `challan_no = :challan_no, challan_date = :challan_date`
  in the SQL, passing the *current* DB values when the caller passes
  None. Simple, but adds a SELECT.
- **B.** Build the UPDATE statement conditionally — only include the
  columns when the caller passes non-None values.

Recommendation: **B**, because (a) the only caller in scope (the final
step) will always pass non-None values, so the conditional path is the
hot path; and (b) it cleanly matches "don't touch what wasn't asked."

## Editor

No changes needed. The editor at `jute_mr_editor.py:707` already passes
`step_to_save.get("challan_date")` for every step including the final one,
so the user override path is already in place.

## Test plan

1. **Final-step inheritance.** Build a 3-step chain ending at the source
   company. Confirm that after finalization the source MR's `challan_no`
   matches the invoice challan_no created on the final hop, and the
   `challan_date` matches `step.challan_date` (when set) or that invoice's
   challan_date.

2. **Mukam preservation.** Confirm `mukam_id` on the source MR is
   unchanged before vs. after finalization.

3. **Revert.** After `delete_chain_from_step` reverts the finalization,
   confirm `challan_no`/`challan_date` are restored — or at least left
   in a reasonable state. (Note: `revert_original_mr` today does not
   touch challan fields either, so this may need a paired fix. Flag in
   plan.)

## Out of scope

- Any change to `_create_sales_invoice()`, `_create_mr()`, or the
  intermediate-step path.
- Any change to `revert_original_mr` beyond the test-plan flag above.
- Any UI changes.
